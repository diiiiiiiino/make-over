## 2. 트래픽 (평상시 / 피크)

| 경로 | 평상시 평균 | 일일 피크 | Meridian Day 피크 |
|---|---|---|---|
| API Gateway 전체 | 950k RPS | 1.6M RPS | **2.4M RPS** |
| **PDP 조회 (우리 팀)** | **420k RPS** | 680k RPS | **1.1M RPS** |
| 검색 | 180k RPS | 310k RPS | 520k RPS |
| 장바구니 담기 | 9k RPS | 22k RPS | 74k RPS |
| 주문 생성 | 1.4k orders/s | 3.2k orders/s | **11k orders/s** |
| 결제 승인 | 1.3k TPS | 3.0k TPS | 9.5k TPS |

### 트래픽 특성

- **읽기:쓰기 = 약 940:1.** PDP는 압도적으로 읽기 시스템이다.
- **롱테일이 심하다.** 상위 0.1% 상품이 조회의 38%를 차지하지만, 하위 60% 상품도 합치면 일 20억 조회다. → 단순 LRU 캐시로는 부족하다.
- **핫키(hot key) 문제**: 신제품 출시/TV 노출 시 단일 상품이 초당 8만 건 이상 조회된다. Redis 단일 샤드가 죽는다.
- **트래픽 급증 패턴**: 광고 메일 발송 후 90초 안에 평상시의 6배가 들어온다. 오토스케일링(2~3분)보다 빠르다. → **사전 워밍 또는 헤드룸 확보가 필수.**
- **봇 비중**: 전체 요청의 약 31%가 가격 크롤러/스크래퍼. 이것도 처리해야 한다.

## 4. SLO (Service Level Objective)

PDP 조회 API는 **Tier-0** (매출 직결, 장애 시 전사 인시던트).

| 지표 | 목표 | 측정 |
|---|---|---|
| 가용성 | **99.99%** (월 에러버짓 4분 22초) | 5xx + 타임아웃 비율 |
| PDP 조회 p50 | ≤ 25ms | 서버 사이드 |
| PDP 조회 p99 | **≤ 120ms** | 서버 사이드 |
| PDP 조회 p99.9 | ≤ 350ms | 서버 사이드 |
| 캐시 히트율 | ≥ 98.5% | 오리진 보호의 핵심 |
| 가격 데이터 신선도 | 변경 후 **5초 이내** 반영 (p99) | 잘못된 가격 노출은 법적 리스크 |
| 재고 표시 정확도 | ≥ 99.2% | 틀리면 주문 취소 → CS 폭증 |

### 오류 예산 정책
- 에러 버짓 50% 소진 → Diego가 경고. 신규 기능 배포 시 카나리 기간 2배.
- 에러 버짓 100% 소진 → **기능 배포 동결.** 안정화 작업만 허용. (서지훈의 로드맵이 밀린다 → 갈등 발생)

## 5. 비용 제약 (Frugality)

- PDP 팀의 월 인프라 예산: **$1.9M** (컴퓨트 $780k / 캐시 $610k / 네트워크·CDN $340k / 기타)
- **요청 100만 건당 비용 목표: $0.42 이하.**
- 새 기능이 이 단가를 올리면 PRD에 비용 영향 분석을 첨부해야 한다. Elena(VPE)가 본다.
- 예: 상품당 API 호출을 1회 더 늘리면 → 일 360억 호출 추가 → 월 $200k 이상. **"그냥 한 번 더 부르면 되죠"가 안 되는 이유.**

## 6. 의존 서비스와 그 현실

우리가 PDP를 조립하려면 아래 서비스를 호출해야 한다. **모두 언젠가 느려지거나 죽는다.**

| 서비스 | 소유 팀 | p99 | 실측 가용성 | 죽으면? |
|---|---|---|---|---|
| Catalog Core (상품 기본 정보) | Catalog | 15ms | 99.99% | PDP 자체가 불가능 → **하드 디펜던시** |
| Pricing Service (가격/프로모션) | Pricing | 40ms | 99.95% | 캐시된 가격 사용, 단 5분 이상 stale이면 판매 중단 |
| Inventory Service (재고) | Inventory | 65ms | **99.9%** | "재고 확인 중"으로 degrade |
| Delivery Promise (배송 약속) | Logistics | **110ms** | 99.9% | 해당 영역 숨김 (이서연 스펙) |
| Review Aggregate (리뷰 요약) | Community | 30ms | 99.9% | 별점 영역 숨김 |
| Ads Service (스폰서 상품) | Ads | 55ms | 99.5% | 광고 영역 숨김. **절대 PDP를 지연시키면 안 됨** |
| Seller Profile | Seller Exp | 25ms | 99.9% | 셀러명만 표시 |

> 산술적으로: 7개 서비스를 직렬 호출하면 p99 합계가 340ms → **SLO 위반.** 병렬 호출 + 개별 타임아웃 + 부분 실패 허용이 설계의 출발점이다.

## 7. 이 숫자들이 만들어내는 설계 제약

1. **모든 외부 호출에 타임아웃과 폴백이 있어야 한다.** 예외 없다.
2. **캐시가 정답이지만, 캐시 무효화가 곧 정확성 문제다.** 특히 가격.
3. **부분 실패는 정상 상태다.** 200 OK에 일부 필드가 비어있는 응답이 표준이다.
4. **재시도는 위험하다.** 940:1 읽기 비율에서 무분별한 재시도는 오리진을 즉사시킨다.
5. **배포는 점진적이어야 한다.** 1 셀 → 1 리전 → 전체. 자동 롤백 필수.
6. **관측성 없는 코드는 미완성이다.** 새벽 3시에 이 코드의 상태를 알 수 없으면 머지되지 않는다.
