# 일하는 방식 (프로세스)

## 1. 스프린트

- **주기**: 2주
- **의식**:
  | 의식 | 시점 | 목적 |
  |---|---|---|
  | Sprint Planning | 1일차 | PO가 PRD 제시, 팀이 티켓 분해·견적 |
  | Daily Standup | 매일 (15분) | 어제/오늘/블로커. **블로커는 그 자리에서 담당자 지정** |
  | Design Review | 필요 시 | ADR을 Priya/Elena가 리뷰 |
  | Sprint Review (Demo) | 마지막 날 | PO·디자이너·CS 앞에서 시연 |
  | Retrospective | 마지막 날 | 프로세스 개선 |
  | WBR | 매주 화 | 전사 지표 리뷰. 우리 SLO가 깨졌으면 여기서 설명 |

- **속도(velocity)**: PDP 팀 평균 **34 SP / 스프린트** (개발자 4명 기준). 내 개인 몫은 **8~10 SP**.
- **스토리 포인트**: 1(반나절) / 2(1일) / 3(2일) / 5(3~4일) / 8(1주, 쪼개는 걸 검토) / 13(반드시 쪼갠다)

## 2. Definition of Ready (티켓을 시작해도 되는 조건)

- [ ] 인수 조건(AC)이 **검증 가능한 형태**로 작성됨 (박하늘 체크)
- [ ] 비기능 요구사항(지연시간/에러율/비용) 명시 (Diego 체크)
- [ ] 성공 지표와 로깅 스펙 존재 (최민석 체크)
- [ ] 의존성과 폴백 동작 정의됨 (이서연 상태 매트릭스)
- [ ] 견적 완료

## 3. Definition of Done (머지·배포 조건)

- [ ] AC 전부 충족, 단위/통합 테스트 통과 (라인 커버리지 ≥ 80%, **분기 커버리지 ≥ 70%**)
- [ ] Testcontainers 기반 통합 테스트 존재
- [ ] Priya(또는 지정 리뷰어) 승인 — **Tier-0는 승인 2개**
- [ ] OpenAPI 스펙 갱신 + 계약 테스트 통과
- [ ] 메트릭/트레이스/구조화 로그 추가, 대시보드 갱신
- [ ] 알람(alert) 정의 및 런북(runbook) 링크
- [ ] 피처 플래그로 감싸짐, 롤백 절차 문서화
- [ ] 부하 테스트 결과가 SLO 만족 (Tier-0 변경 시)
- [ ] 보안 체크리스트 통과 (Noah)

## 4. 코드 리뷰 규칙

- PR은 **400줄 이하**를 권장. 넘으면 쪼갠다.
- PR 설명에 반드시 포함: *무엇을 / 왜 / 어떻게 검증했는지 / 롤백 방법*
- 리뷰어는 24시간 내 1차 응답.
- 리뷰 코멘트 등급:
  - `[blocking]` — 고치기 전엔 승인 불가
  - `[should]` — 강하게 권하지만 반론 가능
  - `[nit]` — 취향, 무시해도 됨
- **반론은 환영된다.** 근거를 대면 Priya는 자기 의견을 철회한다. 단 근거 없이 우기면 안 된다.

## 5. 배포 파이프라인

```
merge → CI(빌드/테스트/정적분석/SCA) → 스테이징 배포 → 통합·계약 테스트
      → 카나리 1셀(1%) 30분 → 1리전 25% 1시간 → 전 리전 순차
```
- 각 단계에서 **자동 롤백 조건**: 에러율 > 0.1%, p99 > SLO의 120%, 5분 지속
- 금요일 오후 3시 이후 배포 금지 (변경 동결)
- Meridian Day 2주 전부터 전면 변경 동결 (핫픽스 제외)

## 6. 온콜과 장애 대응

- 로테이션: 1주 단위. 나도 참여한다.
- 심각도:
  | Sev | 정의 | 대응 |
  |---|---|---|
  | Sev-1 | 매출 중단, 전 리전 영향 | 즉시 호출, 15분 내 전사 공지, CEO 보고 |
  | Sev-2 | 일부 기능/리전 저하 | 30분 내 대응 |
  | Sev-3 | 성능 저하, 우회 가능 | 업무 시간 대응 |
- **모든 Sev-1/2는 COE(포스트모템) 작성.** 비난 없이, 5 Whys로 시스템 원인을 찾는다.
- 원칙: **완화(mitigate) 먼저, 원인 분석은 그 다음.** 롤백을 부끄러워하지 않는다.

## 7. 티켓 워크플로

```
Backlog → Ready → In Progress → In Review → QA → Staging → Done
                       ↑                      │
                       └───── 반려 ───────────┘
```

## 8. 문서 규칙

- 기술 선택은 **ADR**로 남긴다 (`docs/adr/ADR-XXX-*.md`).
- 제품 요구사항은 **PRD** (`backlog/sprint-XX/PRD-XXX-*.md`).
- 장애는 **COE** (`docs/coe/`).
- 문서에 "나중에 정하기로 함"이 있으면 반드시 담당자와 기한을 적는다.
