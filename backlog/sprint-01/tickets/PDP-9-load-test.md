# [PDP-9] Gatling 부하 테스트 — 평상시 420k RPS / 피크 1.1M RPS

**타입**: Task ・ **SP**: 5 ・ **담당**: 나 ・ **요구자**: Diego Alvarez
> 🚧 **이 티켓 통과 없이는 프로덕션 배포 승인이 나지 않는다.**

## 배경
11월 Meridian Day에 1.1M RPS가 들어온다. 10월 중순부터 변경 동결이다. 지금 증명하지 못하면 그때는 손댈 수 없다.

## 해야 할 일
Gatling(Java DSL) 시나리오 작성 및 실행. 인스턴스 단위 → 클러스터 단위 순으로 외삽.

### 필수 시나리오
| # | 시나리오 | 목적 |
|---|---|---|
| L1 | 정상 부하 (캐시 히트 98.5%) | SLO 기준선 |
| L2 | 콜드 캐시 (히트율 0%에서 시작) | 배포 직후/캐시 장애 후 복구 상황 |
| L3 | **핫키** — 단일 상품에 트래픽 40% 집중 | 8만 RPS 핫키 대응 검증 |
| L4 | **스파이크** — 90초 만에 6배 급증 | 광고 메일 발송 패턴. 오토스케일링보다 빠르다 |
| L5 | 롱테일 — 히트율이 낮은 저빈도 상품 위주 | 오리진 부하 |
| L6 | 의존성 열화 — Inventory p99를 500ms로 주입한 상태에서 정상 부하 | 격리 검증 |
| L7 | Meridian Day — 1.1M RPS, 30분 지속 | 최종 관문 |

## 인수 조건
- [ ] **AC1.** L1에서 p50 ≤ 25ms, p99 ≤ 120ms, p99.9 ≤ 350ms.
- [ ] **AC2.** L3에서 오리진(Catalog Core) 호출량이 12k RPS를 넘지 않는다.
- [ ] **AC3.** L4에서 에러율이 0.1%를 넘지 않는다. (셰딩을 쓴다면 그것도 설계의 일부로 인정)
- [ ] **AC4.** L6에서 Inventory 지연이 다른 의존성 응답 시간에 영향을 주지 않는다 (벌크헤드 증명).
- [ ] **AC5.** L7에서 SLO를 만족하며, 필요한 인스턴스 수와 **월 예상 비용**을 산출한다. (100만 요청당 ≤ $0.42)
- [ ] **AC6.** 결과를 표/그래프와 함께 문서화하고, **어디서 먼저 병목이 오는지** 명시한다.
- [ ] **AC7.** 부하 테스트가 CI에서 축소 버전(스모크)으로 자동 실행된다.

## 명시되지 않은 것
- 로컬/스테이징에서 1.1M RPS를 실제로 재현할 수는 없다. **어떻게 외삽할 것이며 그 가정의 한계는 무엇인가?** Diego가 이 답변을 가장 중요하게 본다.
