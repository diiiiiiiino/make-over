# [PDP-5] 2계층 캐시(L1 Caffeine + L2 Redis)와 스탬피드 방지

**타입**: Story ・ **SP**: 5 ・ **담당**: 나 ・ **요구자**: Diego Alvarez
**선행**: PDP-1 (ADR-001)

## 배경
캐시 히트율이 91.2%다. 420k RPS의 8.8% = **37k RPS가 Catalog Core로 간다.** 그 팀의 용량은 12k RPS다. 지금은 레거시 캐시가 우연히 버티고 있을 뿐이다.
Diego: *"98.5% 못 맞추면 우리가 Catalog을 죽입니다. 그리고 그건 전사 Sev-1입니다."*

## 해야 할 일
- L1: Caffeine (인스턴스 로컬)
- L2: Redis Cluster
- 읽기 경로: L1 → L2 → 오리진, 각 단계 승격(promotion)
- **스탬피드 방지**: 동일 키에 동시 미스가 발생해도 오리진 호출은 1회
- 핫키 대응: 단일 상품 8만 RPS 시나리오 대응책

## 인수 조건
- [ ] **AC1.** 캐시 히트율 메트릭이 L1/L2/오리진으로 구분돼 측정된다.
- [ ] **AC2.** 동일 키에 대해 **동시 1,000개 요청이 미스**일 때 오리진 호출이 1회임을 테스트로 증명한다.
- [ ] **AC3.** Redis 전체 장애 시 서비스가 죽지 않고 L1 + 오리진으로 degrade하며, 오리진 보호 장치(레이트리밋/셰딩)가 동작한다.
- [ ] **AC4.** 캐시 키 설계가 ADR-001과 일치하며, 마켓플레이스/통화가 섞이지 않는다. (**KR 고객에게 USD 가격이 보이면 Sev-1이다**)
- [ ] **AC5.** 부분 실패(degraded) 응답의 캐시 정책이 명시적으로 결정되고 구현됐다.
- [ ] **AC6.** TTL 만료가 한 시점에 몰리지 않도록 지터가 적용됐다.

## 비기능 요구사항
| 항목 | 기준 |
|---|---|
| 히트율 | ≥ 98.5% (L1+L2) |
| L1 조회 | p99 ≤ 1ms |
| L2 조회 | p99 ≤ 5ms |
| 메모리 | L1이 힙의 40%를 넘지 않을 것 (GC 압박) |

## 명시되지 않은 것
- L1과 L2의 TTL을 다르게 가져갈 것인가? 다르면 불일치는 어떻게 처리하나?
- Redis에 무엇을 저장하나 — 조립된 최종 응답? 아니면 의존성별 조각?
  → **이 결정이 무효화(PDP-6) 난이도를 결정한다.** 김도현과 반드시 협의할 것.
